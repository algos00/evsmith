# AGENTS.md

Working notes for anyone (human or AI agent) changing this repository. The README is for users; this file is for
people who edit the code. Facts below were checked against the repo and GitHub on 2026-11-19; if something here no
longer matches the code, fix this file in the same commit.

## What this is

EVSmith: a Stat Point spread optimizer for **Pokémon Champions** (level 50, doubles, VGC). You state what your
Pokémon must survive, KO and outspeed; it finds the 66-point spread (max 32 per stat) that does it with the fewest
points. Everything runs in the browser; there is no server and no tracking.

- Ships as one HTML file, `dist/EVSmith.html` (about 440 KB), plus `sw.js`, `manifest.webmanifest` and `icons/` next to it
  for the installable/offline version (only used when served over http/https).
- Repository: `github.com/algos00/evsmith` (public, MIT). Live: https://algos00.github.io/evsmith/ (GitHub Pages).
- Unofficial fan project. Never imply affiliation with Nintendo, Game Freak, Creatures or The Pokémon Company. Sprites
  and artwork are **not** stored in the repo; the page loads them at runtime from the PokéAPI sprites repository. The one
  exception is the 3D hero model `src/hero/garchomp.glb` (CC BY 4.0, by Icefer547 on Sketchfab, textures reduced to 1024 px WebP):
  keep its credit in the footer (`template.html`) and in the README, and say so if the model changes.
- No runtime dependencies in the app. Node >= 20 is only needed to build and test. Test dependencies live in `tests/`
  (`@smogon/calc` pinned to 0.12.0, `puppeteer-core`). `tools/` has its own dependencies (`three`, `esbuild`) used only to
  bundle the 3D hero; the bundle `src/hero/hero.js` is committed, so building and CI never need them.

## Conventions

- Chat with the maintainer is in Italian. Code, comments, commit messages, issues and docs are in English. The only
  Italian in the repo is the interface translation (`src/i18n.it.js`) and a few older comments in `src/ui.js`.
- Commit subjects: short, imperative, no prefix (`Fix header pictures overlapping the text at 1000-1199px`,
  `Release 1.3.0`). History on `main` is linear; no branch policy has been set.
- Edit `src/`, never `dist/` (it is git-ignored and rebuilt).
- Do not hand-edit generated files: `src/data.js`, `src/tdata.js`, `src/sprites.js`.
- For a non-trivial change, agree on the plan with the maintainer first (files touched, behaviour, alternatives).
- Report test results as they are: failures, skipped steps and things not run.

### Things that break quietly

- **The 3D hero** exists only over http/https (the loader in `template.html` adds `<html class="has-stage">`); from `file://`, without WebGL, on a lost context or if `hero/` fails to load, the class is removed and the old header (`.top`) shows. Both headers carry the same logo/h1/tagline, so edit both. After changing `hero.src.js` run `npm install --prefix tools && node tools/build-hero.js` and commit `hero.js`. The e2e blocks `/hero/` in every page except the "3D hero" test, because software WebGL made the others several times slower. Not tested: the hero offline (the service worker caches it only after a first view) and real-GPU or Safari/Firefox rendering.

- **Content-Security-Policy.** `build.js` hashes every inline `<script>` and writes the CSP. `connect-src 'self' blob:`, `script-src` has `'self'` for the hero module, images only
  from `'self'`, `data:`, `blob:` and `raw.githubusercontent.com` (`blob:` is what the glTF loader needs for the model's WebP textures), fonts only from Google Fonts. A new external resource or network
  call needs a deliberate CSP change in `build.js`; always rebuild after touching a script.
- **Test loader markers.** `tests/lib/load.js` cuts the optimizer core out of `src/ui.js` between the text
  `var A=ENG;` and the comment `/* ---------- UI ---------- */`, and pulls `newField`, `flatField`, `oppCfg`, `newGoal` by
  name. Moving or renaming those breaks every test that loads the app. New functions the tests need go into the `SOLVE`
  export at the bottom of `load.js`.
- **Translations.** Keys of `I18N_IT` are the exact English strings used in `template.html` (`data-i18n`,
  `data-i18n-ph`, `data-i18n-title`) and in `ui.js` (`tr()`, `N_()`). Change an English text and its key must change too;
  `tests/i18n.js` reports missing and unused keys. Game names (Pokémon, moves, abilities, items, natures) stay in English.
- **Browser storage keys:** `evsmith.state.v1` (saved form) and `evsmith.lang`. Share links use `#s=`. Changing the state
  format must stay readable by old saved states and old links (`cleanState`, `decodeShare`).
- **Service worker cache** is named after the version (`evsmith-<version>-shell`); a release invalidates it by itself.
- **Tournament data requests** wait 10 s between calls (the site's robots.txt crawl delay). Do not lower it.

## Commands

```
npm ci --prefix tests     # test dependencies, once
npm run build             # writes dist/
npm test                  # build + quick checks (use while developing)
npm run test:full         # build + everything, end-to-end in Chrome included (before a release; CI runs this)
npm run update-meta       # refresh src/tdata.js (about 11 minutes, network)
npm run update-sprites    # refresh src/sprites.js (one request)
```

Single checks, from `tests/`: `node compare-smogon.js [seed] [cases]`, `node optimizer-bruteforce.js [seed] [scenarios]
[autoNatureScenarios] [k/n]`, `node situational.js`, `node features.js`, `node app-logic.js`, `node contrast.js`,
`node i18n.js`, `node e2e.js`. A failing check in `run-all.js` prints the exact command to reproduce it. `EVSMITH_HTML=path`
tests another build; `CHROME_PATH` selects Chrome for the e2e (without Chrome it is skipped locally and fails in CI).

### What to run when

- Changed text, CSS or markup only: `npm test` (the layout check is in the e2e, so run `npm run test:full` if you touched the
  header or any layout).
- Changed `engine.js`, `ui.js` optimizer code or data: `npm run test:full`.
- Before tagging a release: `npm run test:full`, no exceptions (see Release).

## Tests and timings

What each check does is in `tests/README.md`. In short: the damage engine and the situational abilities are compared with
`@smogon/calc` on random cases; the optimizer is compared with an exhaustive search; `features`, `app-logic`, `contrast`,
`i18n` cover the rest; `e2e` drives the built page in real Chrome (keyboard use, calculation, import, share link, layout at
10 widths, accessibility names, Italian interface, offline mode).

Timings on the maintainer's machine (12 logical cores, shared with other work, so they vary by 10-20%):

| date | change | quick | full |
|---|---|---|---|
| 2026-11-19 | before the speed-up | 4.7 s | 79.3 s (parallel part 56.5 s + e2e 22.7 s) |
| 2026-11-19 | after the speed-up | 3.4-3.9 s | 32-37 s (parallel part about 15.5 s + e2e 16-20 s) |

The CPU time of the full run went from about 560 s to about 155 s. What changed:

- `optimizer-bruteforce.js`: the reference search computes the damage rolls once per defensive value instead of once per
  (HP, defence) pair (33 engine calls instead of 1089 per table). The search stays exhaustive: every value is also computed
  at 0 and 32 HP points and the two must agree, otherwise the test fails with "damage depends on HP points". This made the
  "every nature" and Foul Play scenarios (the old long pole, 20-55 s each) take 4-5 s.
- `run-all.js`: a work queue of processes (slowest checks first) instead of one fixed shard per process, with a number of
  optimizer parts tied to the core count (more only adds start-up time: each process loads the app).
- `e2e.js`: the layout test opens its 10 widths in parallel in a second Chrome, so it overlaps the other e2e checks.

Notes learned while doing it:

- The e2e runs **after** the parallel checks on purpose. Run alongside them (even with 2 cores kept free) about 1 run in 5
  failed with "Waiting for selector `#acbox:not([hidden])` failed" (the suggestion list did not open after typing; the cause was
  not investigated). `pickWithKeyboard` retries typing up to 3 times as protection. Do not run several e2e at once, and do not put
  layout (or other tests that open/close pages) in the same Chrome as the keyboard tests.
- What is left in the optimizer test is mostly the app's own solver (`mS`, `conv`, `nm` in the profile), not the test code.
  Speeding up the solver would speed up both the app and the tests; it is product code, so it needs its own decision.
- The tolerated numbers of unexplained engine differences (0.05% of cases) and the "expected Champions-data differences"
  are explained in `tests/README.md`; do not raise them to make a run pass.

## CI and repository settings

- `test.yml`: runs `npm run test:full` on every push to `main` and on pull requests (Node 22, `ubuntu-latest`).
- `release.yml`: runs on a pushed `v*` tag. Checks that the tag equals `package.json` version, runs `npm run test:full` again,
  builds, creates the GitHub Release with `EVSmith-vX.Y.Z.html` attached, and deploys GitHub Pages when the repository variable
  `PUBLISH_PAGES` is `true` (it is).
- `update-meta.yml`: Mondays 05:17 UTC (and on demand) refreshes `src/tdata.js` and opens a pull request if it changed. The
  PR is opened with the workflow token, so the *Test* workflow does **not** start by itself on it: run the checks (or push an
  empty commit) before merging. Needs *Settings → Actions → General → Allow GitHub Actions to create and approve pull requests*.
  Merging and releasing stay manual.
- The repository *About* description is empty; the README says where the live page is.

## Release (deploy)

A release is a version tag. Pushing the tag builds, tests, publishes the GitHub Release and updates the live page.

1. Make sure `main` has everything you want and the working tree is clean.
2. Run `npm run test:full` **locally** and see it pass. The quick set does not include the end-to-end checks; the first 1.3.0 run
   failed in CI on the e2e layout check (a header overlap), which only the full set runs.
3. Choose the version (semantic: fixes `X.Y.Z+1`, features `X.Y+1.0`). Set `version` in `package.json` and add a section to
   `CHANGELOG.md` (user-visible changes; the changelog does not list test or tooling work unless it matters to users).
4. Commit as `Release X.Y.Z` and push `main`. Wait for the *Test* workflow on that commit to be green
   (`gh run watch`, or `gh run list -L3`).
5. Tag that same commit and push the tag: `git tag vX.Y.Z && git push origin vX.Y.Z`.
6. Watch the *Release* workflow (`gh run watch`). Then check `gh release view vX.Y.Z` (the HTML file is attached) and that
   https://algos00.github.io/evsmith/ shows the new version in the footer.

### Never move a published tag: ship a patch version instead

If anything is wrong after a tag was pushed (the *Release* workflow failed, a bug was found, a file is missing), **do not delete,
re-create or force-push the tag**, even when the Release workflow failed before publishing anything. Fix the problem on `main`
and release the next patch number (for example `v1.3.1` after a problem with `v1.3.0`): bump `package.json`, add the
changelog entry, run `npm run test:full`, commit `Release 1.3.1`, tag `v1.3.1`.

Why: people may already have downloaded `EVSmith-v1.3.0.html`, and the service worker, Pages and the Release page all
identify a build by its version; two different builds with the same number cannot be told apart. History: `v1.3.0` was moved
once (the first *Release* run failed on the header-overlap check, the fix was committed and the tag re-pointed at the fix). It is
the only move visible in the Actions history, and it is the reason for this rule. A failed tag is cheap: leave it (and its failed run) alone and publish the
next patch.

A release that has already been published and turns out bad can be marked as pre-release or edited in the GitHub UI, but the
fix is always a new version.
